Scale từ 1 server đến millions

Chương 1 dẫn từng bước: tách DB → load balancer → replication → cache → CDN → sharding. Đọc chậm, mỗi bước tự hỏi hệ thống mình đang làm nằm ở đâu trong chuỗi đó. Song song, làm 5 bài ước lượng bằng giấy, 15 phút mỗi bài, đến khi thành phản xạ.

Kiến thức1 triệu request mỗi ngày là bao nhiêu QPS? Peak là bao nhiêu? Một server có đủ không?
Đáp án đạt
  • 1 ngày ≈ 10⁵ giây ⇒ 10⁶ / 10⁵ ≈ 10–12 QPS trung bình.
  • Nêu giả định peak (thường ×2–×5) ⇒ vài chục QPS.
  • Kết luận: một server vừa đủ, chưa cần scale ngang — nhưng nên chừa single point of failure (≥2 server sau load balancer).
Kiến thứcWeb tier cần stateless để làm gì, và session đưa đi đâu?
Đáp án đạt
  • Stateless để thêm/bớt server tuỳ ý sau load balancer, request nào vào server nào cũng được.
  • Session/state đẩy ra kho dùng chung (Redis hoặc NoSQL), không giữ trong bộ nhớ web server.
Kiến thứcNêu 4 bước của khung phỏng vấn và chia thời gian cho 45 phút.
Đáp án đạt
  • 1) Hiểu đề + chốt scope: 3–10′. 2) Thiết kế high-level + xin buy-in: 10–15′. 3) Deep dive: 10–25′. 4) Wrap-up: 3–5′.
  • Điểm trừ lớn nhất: vẽ ngay mà không hỏi, hoặc nhảy vào chi tiết khi chưa được đồng ý với bản high-level.
ClarifyĐề: “Thiết kế news feed”. Ba câu hỏi đầu tiên của bạn?
Đáp án đạt
  • Mobile, web hay cả hai? Tính năng cốt lõi: đăng bài, xem feed (có ảnh/video không)?
  • Feed sắp xếp theo thời gian hay ranking? Mỗi người tối đa bao nhiêu bạn bè?
  • Quy mô: bao nhiêu DAU, QPS đọc/ghi? — rồi mới vẽ.

Building block

Load balancer, cache, CDN, replication, sharding, SQL/NoSQL, message queue, consistency model. Mỗi cái chỉ cần trả lời ba câu: dùng khi nào, trả giá gì, vỡ ở đâu khi scale. Consistent hashing để cuối tuần.

VỡCache chết thì hệ thống chậm đi hay sập hẳn?
Đáp án đạt
  • Với cache-aside: toàn bộ read đổ về DB. Nếu hit ratio 90%, DB đột ngột nhận gấp ~10× tải đọc ⇒ có thể sập (cache stampede).
  • Giảm nhẹ: cache nhiều replica/cluster, warm-up trước khi nhận traffic, gộp request cùng key, rate limit ở DB.
Kiến thứcConsistent hashing giải quyết gì so với hash(key) % N? Virtual node để làm gì?
Đáp án đạt
  • hash % N: thêm/bớt server làm gần như mọi key đổi server ⇒ cache miss hàng loạt.
  • Consistent hashing: chỉ di chuyển phần key liền kề trên vòng (≈ k/n key).
  • Virtual node: mỗi server nhiều điểm trên vòng ⇒ phân phối đều hơn, tránh hotspot.
VỡUser đăng bài xong reload không thấy bài của mình (replication lag). Xử lý sao?
Đáp án đạt
  • Read-your-writes: một khoảng ngắn sau khi ghi thì đọc từ primary (hoặc định tuyến theo timestamp lần ghi).
  • Người khác thấy chậm vài giây là chấp nhận được (eventual consistency).
Kiến thứcKhi nào chọn NoSQL thay vì SQL?
Đáp án đạt
  • NoSQL khi cần latency rất thấp, dữ liệu phi cấu trúc/không quan hệ, hoặc khối lượng dữ liệu khổng lồ cần scale ngang.
  • Mặc định vẫn là SQL khi cần quan hệ, transaction, ACID.

URL shortener

Case dễ nhất, nên dùng nó để tập quy trình chứ không phải để học kiến thức mới. Làm lần hai cách lần một vài ngày. Đây cũng là tuần đầu tiên bắt buộc nói to thành tiếng như đang giải thích cho người khác.

Hash hay counter, và va chạm thì xử lý thế nào?
Kiểm tra cuối tuần · 4 câu
ClarifyHỏi gì trước khi vẽ URL shortener? Con số bạn kỳ vọng?
Đáp án đạt
  • Lượng URL mới/ngày, tỉ lệ đọc:ghi, độ dài URL ngắn, ký tự cho phép, có xoá/cập nhật không, thời hạn lưu.
  • Ví dụ trong sách: 100 triệu URL/ngày ≈ 1.160 write/s; đọc:ghi = 10:1 ≈ 11.600 read/s; lưu 10 năm ≈ 365 tỉ bản ghi.
Kiến thứcĐộ dài mã ngắn tối thiểu là bao nhiêu? Hash + xử lý va chạm hay base62 từ ID?
Đáp án đạt
  • 62⁷ ≈ 3,5 nghìn tỉ > 365 tỉ ⇒ 7 ký tự là đủ.
  • Hash (CRC32/MD5/SHA-1 cắt 7 ký tự): ngắn cố định nhưng va chạm ⇒ phải kiểm tra DB (bloom filter giảm query) rồi hash lại.
  • Base62 từ ID duy nhất: không va chạm, nhưng độ dài tăng dần và ID đoán được; cần bộ sinh ID phân tán.
Kiến thức301 hay 302? Ảnh hưởng thế nào?
Đáp án đạt
  • 301 (permanent): trình duyệt cache ⇒ giảm tải server nhưng mất số liệu click.
  • 302 (temporary): mỗi lần click đều qua server ⇒ làm analytics được. Chọn theo yêu cầu.
×10Traffic ×10 thì cái gì vỡ trước?
Đáp án đạt
  • Đọc vọt lên >100K QPS: URL phổ biến lặp lại nhiều ⇒ cache (Redis) hấp thụ phần lớn; thêm read replica.
  • DB lưu trữ ~vài chục TB: shard theo hash của mã ngắn khi cần. Thêm rate limiter chống abuse.

Rate limiter · Unique ID

Hai case ngắn cùng dạy một kỹ năng: chọn thuật toán rồi bảo vệ lựa chọn đó. Token bucket cho phép burst, sliding window thì mượt hơn nhưng tốn bộ nhớ. Bên kia là Snowflake, và chuyện gì xảy ra khi NTP kéo đồng hồ nhảy ngược.

ClarifyRate limiter: hỏi gì trước?
Đáp án đạt
  • Client-side hay server-side (middleware/API gateway)? Giới hạn theo IP, user hay key khác? Quy mô, môi trường phân tán?
  • Có cần thông báo cho user bị chặn: trả HTTP 429 kèm X-Ratelimit-Remaining / X-Ratelimit-Limit / Retry-After.
Kiến thứcSo sánh token bucket, fixed window và sliding window. Chọn cái nào?
Đáp án đạt
  • Token bucket: 2 tham số (bucket size, refill rate), cho phép burst, tốn ít bộ nhớ (Amazon, Stripe dùng).
  • Fixed window: burst ở rìa cửa sổ có thể cho qua gấp đôi quota.
  • Sliding window log: chính xác nhưng tốn bộ nhớ (lưu timestamp); sliding window counter: xấp xỉ, nhẹ — nói rõ trade-off.
VỡCounter đặt ở Redis thì race condition xử lý sao? Nhiều rate limiter thì đồng bộ thế nào?
Đáp án đạt
  • Đọc-rồi-ghi (get/set) không nguyên tử ⇒ 2 request cùng thấy cùng giá trị. Dùng Lua script hoặc sorted set để thao tác nguyên tử.
  • Nhiều instance: dùng kho dùng chung (Redis tập trung) thay vì sticky session.
Kiến thứcSnowflake ID gồm những phần nào? Khi NTP kéo đồng hồ nhảy ngược thì sao?
Đáp án đạt
  • 1 bit dấu, 41 bit timestamp, 5 bit datacenter, 5 bit machine, 12 bit sequence ⇒ 4096 ID/ms/máy.
  • Đồng hồ lùi có thể sinh ID trùng/ngược thứ tự: từ chối sinh/ chờ tới khi đồng hồ vượt mốc cuối, dùng NTP chỉnh dần thay vì nhảy.

Key-value store nặng

Nặng nhất Vol 1 và cũng là bài trả cổ tức: quorum, vector clock, LSM tree, SSTable, Merkle tree. Học xong thì mọi case sau nhẹ đi một nửa vì các khái niệm này quay lại liên tục. Hiểu được 70% là đi tiếp, đừng kẹt lại chờ hiểu hết.

Kiểm tra cuối tuần · 4 câu
Kiến thứcR + W > N cho bạn cái gì và trả giá bằng cái gì?
Đáp án đạt
  • N bản sao, W = số node phải ack ghi, R = số node phải trả lời đọc. R + W > N ⇒ tập đọc và tập ghi luôn giao nhau ⇒ đọc thấy bản mới nhất (strong consistency).
  • Giá phải trả: latency bị quyết định bởi node chậm nhất trong quorum; W=1,R=N ghi nhanh/đọc chậm và ngược lại.
Kiến thứcKV store kiểu Dynamo chọn gì trong CAP? Khi network partition thì sao?
Đáp án đạt
  • Chọn AP: vẫn nhận ghi ở cả hai phía partition, chấp nhận không nhất quán rồi hoà giải sau (vector clock, anti-entropy).
  • CP sẽ chặn ghi ở phía không đủ quorum.
Kiến thứcPhát hiện lỗi, xử lý lỗi tạm thời và vĩnh viễn như thế nào?
Đáp án đạt
  • Gossip protocol (heartbeat counter) thay vì multicast — không scale.
  • Lỗi tạm thời: sloppy quorum + hinted handoff. Lỗi lâu dài: anti-entropy bằng Merkle tree để đồng bộ bản sao.
  • Xung đột phiên bản: vector clock [server, version] — nhược: phức tạp, vector dài.
Kiến thứcMô tả write path và read path của một node.
Đáp án đạt
  • Ghi: commit log → memtable → khi đầy thì flush thành SSTable.
  • Đọc: memtable → bloom filter chỉ ra SSTable nào có thể chứa key → đọc SSTable (merge).

Kiến thứcQueue giao at-least-once thì consumer phải làm gì?
Đáp án đạt
  • Idempotent: dedupe theo event ID (đã xử lý/gửi chưa thì bỏ qua).
  • Retry kèm exponential backoff. Không thể đảm bảo exactly-once, chỉ giảm trùng bằng dedupe.
VỡProvider push notification (hoặc SMS) chậm/chết thì sao?
Đáp án đạt
  • Mỗi loại thông báo (iOS, Android, SMS, email) một queue riêng ⇒ cô lập lỗi, không kéo cả hệ thống.
  • Lưu notification log vào DB trước khi gửi để retry khi crash.
Kiến thứcWeb crawler: BFS hay DFS? URL frontier giải quyết những gì?
Đáp án đạt
  • BFS (DFS có thể đi sâu vô hạn). Frontier lo: politeness (mỗi host một queue, 1 worker/host + delay), priority, freshness.
  • Tôn trọng robots.txt (tải và cache).
Kiến thứcTránh crawl trùng và spider trap thế nào?
Đáp án đạt
  • Bloom filter / lưu hash URL đã gặp; hash nội dung để phát hiện trang trùng.
  • Spider trap: giới hạn độ dài URL/độ sâu, blacklist thủ công.

News feed

Bài kinh điển nhất trong mọi vòng phỏng vấn. Fanout on write cho đọc nhanh nhưng chết với tài khoản 50 triệu follower; fanout on read thì ngược lại. Đáp án thật là giải pháp lai. Feed ranking để sau, đừng sa đà.

Kiến thứcĐẩy bài lúc ghi hay lúc đọc? Ngưỡng nào thì đổi?
Đáp án đạt
  • Fanout on write: feed dựng sẵn ⇒ đọc nhanh; nhưng tốn ghi/lãng phí cho user không active và quá nặng với celebrity.
  • Fanout on read: không lãng phí nhưng đọc chậm.
  • Hybrid: push cho đa số, pull cho tài khoản nhiều follower; ngưỡng dựa trên chi phí fanout so với độ trễ đọc, đo thực tế rồi cấu hình.

  • 5 tầng: news feed, content, social graph, action, counters.
  • Nêu cái nào hot nhất (news feed ID + content) và lý do tách để cache độc lập.
VỡCelebrity 50 triệu follower đăng bài thì sao?
Đáp án đạt
  • Fanout on write = 50 triệu lần ghi ⇒ không làm; chuyển sang pull cho tài khoản này, gộp vào feed lúc đọc.
  • Dùng consistent hashing để giảm hotkey.
×10DAU ×10 thì chỗ nào vỡ trước?
Đáp án đạt
  • Fanout service/queue, cache feed, graph DB. Scale bằng thêm worker fanout, shard cache theo user, queue để làm mượt burst.

Chat

Bài dễ ghi điểm nhất cho fullstack vì bạn hiểu phía client. Long-polling vs WebSocket, presence, offline delivery, ack. Nhớ rằng chat 1-1 và group 100 nghìn người có kiến trúc khác hẳn nhau — hỏi scope trước khi vẽ.

Kiến thứcLong-polling, WebSocket, SSE: khác gì, chọn gì cho chat?
Đáp án đạt
  • WebSocket: kết nối 2 chiều bền vững, bắt đầu bằng HTTP upgrade (qua firewall được). Dùng cho nhận tin; gửi có thể HTTP hoặc WebSocket.
  • Long-polling: tốn tài nguyên khi không có tin, sender/receiver có thể ở khác server, khó cân bằng. SSE: một chiều server → client.
  • Chat server stateful (giữ kết nối), phần còn lại stateless, dùng service discovery (ZooKeeper) chọn chat server.
Kiến thứcMessage ID sinh ở đâu và ordering dựa vào gì?
Đáp án đạt
  • ID phải sắp xếp được theo thời gian; không dùng created_at vì 2 tin cùng timestamp.
  • Chat 1-1/nhóm chỉ cần sequence tăng dần cục bộ trong từng kênh, không cần toàn cục (Snowflake cũng được).
Kiến thứcPresence (online/offline) làm thế nào?
Đáp án đạt
  • Heartbeat từ client định kỳ (ví dụ 5s); nếu quá ngưỡng (ví dụ 30s) không có thì coi là offline.
  • Fanout trạng thái cho bạn bè qua pub/sub; nhóm lớn thì lấy khi mở nhóm.
×10Chat 1-1 vs group 100K người: kiến trúc khác ở đâu? Offline thì sao?
Đáp án đạt
  • Nhóm nhỏ: mỗi thành viên một inbox/sync queue ⇒ fanout on write được. Nhóm 100K: không copy vào từng inbox được — cần cách đọc/kéo khác.
  • Offline: lưu tin, đẩy push notification, đồng bộ lại từ sync queue khi online; lịch sử lưu ở KV store (HBase/Cassandra) vì dữ liệu khổng lồ, đọc gần đây nhiều.

Hotel reservation · Payment

Nhóm hay bị bỏ qua nhưng rất hay được hỏi cho e-commerce và fintech. Đây là chỗ duy nhất trong lộ trình mà eventual consistency không cứu được bạn: đặt trùng phòng và trừ tiền hai lần đều là lỗi người dùng nhìn thấy ngay.

ClarifyHotel reservation: hỏi gì? Thiết kế đặt phòng theo phòng cụ thể hay loại phòng?

Kiến thứcChống double-booking: lock hay điều kiện trên UPDATE?
Đáp án đạt
  • Hai vấn đề riêng: (1) user bấm 2 lần ⇒ vô hiệu nút phía client + idempotency key (reservation_id làm khoá chính, unique constraint). (2) hai user tranh phòng cuối ⇒ race condition.

Kiến thứcExactly-once trong payment = gì + gì?
Đáp án đạt

  • Request trùng đồng thời: chỉ một được xử lý, còn lại 429/trả kết quả cũ. Với PSP: nonce → token dùng làm idempotency key phía PSP.
Kiến thứcReconciliation để làm gì? Ledger kiểu double-entry nghĩa là gì?
Đáp án đạt
  • Reconciliation = so khớp định kỳ (hằng đêm) settlement file của PSP/ngân hàng với ledger — là tuyến phòng thủ cuối; lệch chia 3 loại: tự động sửa được, phân loại được nhưng sửa tay, không phân loại được.
  • Double-entry: mỗi giao dịch ghi 2 dòng cùng số tiền (ghi nợ/ghi có), tổng mọi dòng = 0.
VỡMỗi microservice một DB thì giữ nhất quán thế nào?
Đáp án đạt
  • 2PC: nguyên tử nhưng blocking, một node lỗi chặn tiến trình. Saga: chuỗi giao dịch cục bộ + giao dịch bù, eventual consistency.

Distributed message queue nên làm nặng

Đây là bài dạy bạn Kafka từ bên trong, và là nền cho mọi case mở rộng sau (metrics, ad click, wallet). Trọng tâm: log tuần tự thay vì DB, partition và consumer group, replication với ISR, ba mức delivery semantics.

Kiểm tra cuối tuần · 5 câu
Kiến thứcVì sao lưu message bằng write-ahead log append-only trên đĩa thay vì database?
Đáp án đạt
  • Truy cập tuần tự: ổ quay RAID đạt vài trăm MB/s, tận dụng OS page cache; không có update/delete ngẫu nhiên.
  • Chia segment file: chỉ ghi vào active segment, segment cũ chỉ đọc và bị cắt khi quá hạn retention. Message giữ nguyên định dạng từ producer → queue → consumer để tránh copy.
Kiến thứcPartition, consumer group, offset liên hệ nhau thế nào? Mô phỏng point-to-point và pub/sub ra sao?
Đáp án đạt
  • Topic chia thành partition (FIFO, offset tăng dần); mỗi group giữ offset riêng. Một partition chỉ 1 consumer trong group để giữ thứ tự; consumer thừa số partition thì ngồi không.
  • Một group duy nhất ≈ point-to-point; nhiều group cùng đọc một topic = pub/sub. Nên cấp đủ partition từ đầu vì giảm partition rất phiền.
Kiến thứcACK = 0 / 1 / all khác gì? ISR để làm gì?
Đáp án đạt
  • 0: gửi không chờ, không retry — nhanh nhất, có thể mất. 1: leader ghi xong là ack — leader chết trước khi replicate thì mất. all: chờ mọi ISR — bền nhất, chậm theo replica chậm nhất.
  • ISR là tập replica ‘đủ kịp’ leader; cân bằng hiệu năng và độ bền; replica phải nằm ở broker khác nhau; controller (bầu bằng ZooKeeper/etcd) lo failover.
Kiến thứcAt-most / at-least / exactly once: commit offset khi nào? Dùng cho case nào?
Đáp án đạt
  • At-most-once: commit offset trước khi xử lý (metrics, mất ít không sao). At-least-once: commit sau khi xử lý, có thể trùng ⇒ consumer dedupe/idempotent (mặc định hợp lý).
  • Exactly-once: đắt và phức tạp, dành cho tài chính (payment, trading). Push vs pull: queue thường chọn pull để consumer tự kiểm soát tốc độ và batch; long polling tránh poll rỗng.
×10Throughput ×10 thì chỉnh gì? Rebalance có vấn đề gì?
Đáp án đạt
  • Thêm partition và consumer, tăng batch size ở producer (đánh đổi throughput lấy latency), thêm broker (tạm thời để dư replica rồi bỏ bản cũ khi bản mới bắt kịp).
  • Hàng trăm consumer thì rebalance có thể mất vài phút ⇒ làm ngoài giờ cao điểm.
